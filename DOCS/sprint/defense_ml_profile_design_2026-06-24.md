# Гибридный ML-профиль для защиты: дизайн

Дата: 2026-06-24

## Цель

Подготовить отдельный профиль `defense`, который на MacBook Pro M3 Pro с 18 ГБ памяти устойчиво выполняет оба демонстрационных направления перевода:

- английская речь → русский текст и TTS;
- русская речь → английский текст и TTS.

Профиль должен использовать дообученные модели там, где их специализация подтверждена, не ухудшать обратное направление и оставаться достаточно быстрым для живой демонстрации.

## Исходные модели

Доступны два пользовательских артефакта:

- `DOCS/nemi-nllb-domain-en-ru` — Transformers checkpoint на базе NLLB/M2M100, дообученный для EN → RU;
- `DOCS/nemi-whisper-domain` — Transformers checkpoint Whisper Small с validation WER около 3,97%.

Fine-tuned NLLB применяется только для EN → RU. Использование этой модели для RU → EN не считается корректным, поскольку обучение и измеренный прирост относятся к одному направлению.

Whisper checkpoint перед эксплуатацией дополняется processor/tokenizer файлами совместимого Whisper Small и конвертируется в CTranslate2 int8. `optimizer.pt`, scheduler, scaler и training state не входят в runtime-модель.

## Архитектура профиля

### STT

Для каждого исходного языка сравниваются:

- fine-tuned Whisper Small int8;
- стандартный faster-whisper Small int8;
- стандартный faster-whisper Medium int8, если его скорость приемлема.

Победитель выбирается отдельно для EN и RU по одинаковому локальному корпусу. Критерии: точность обычной речи, технических терминов и code-switch, затем real-time factor и пиковая память. Профиль не предполагает, что fine-tuned checkpoint автоматически лучше для обоих языков.

Языковая подсказка Whisper становится настраиваемой. Для обычной демонстрации используется выбранный язык комнаты; для mixed-language проверки включается auto/multilingual режим без принудительного `language=ru`, чтобы английские термины не переводились в ошибочную кириллическую фонетику.

### MT

Маршрутизация выполняется по языковой паре:

- `en-US → ru-RU`: fine-tuned NLLB;
- `ru-RU → en-US`: Marian `opus-mt-ru-en`;
- остальные уже поддерживаемые пары: существующая Marian/NLLB конфигурация без изменения контрактов API.

Если fine-tuned NLLB не загружается или превышает установленный лимит времени, EN → RU переключается на Marian. Ошибка модели не должна останавливать аудиопоток.

### Phrase buffer и задержка

TTS не участвует в накоплении контекста. Фраза собирается перед MT.

Начальные параметры defense-профиля:

```text
STT_SEGMENT_MAX_MS=6000
STT_SEGMENT_MIN_MS=0
VAD_PADDING_MS=750
PHRASE_MIN_CHARS=80
PHRASE_MAX_CHARS=300
PHRASE_TIMEOUT_MS=4000
LISTENER_DELAY_MS=1500
```

`STT_SEGMENT_MIN_MS=0` выбран намеренно: текущая VAD-реализация отбрасывает короткие сегменты, а не удерживает их до достижения минимальной длины. Качество фразы обеспечивается `VAD_PADDING_MS`, максимальным STT-окном и `PhraseAggregator`.

Listener delay используется только для упорядоченной доставки. Он не считается источником контекста и не увеличивается ради качества перевода.

### TTS и термины

Piper остаётся монолингвальным:

- английский перевод озвучивается английским голосом;
- русский перевод — русским голосом.

Для технических терминов glossary хранит перевод для текста и произносимую форму там, где русский Piper не может корректно прочитать латиницу. Сначала сохраняется корректный STT-текст; TTS не должен компенсировать ошибки распознавания.

## Runtime-размещение

Исходные training checkpoints остаются в `DOCS/` как пользовательские артефакты и не коммитятся из-за размера. Подготовленные inference-модели размещаются в `models/`:

```text
models/nemi-whisper-domain-ct2-int8/
models/nemi-nllb-domain-en-ru/
```

Docker получает их через уже существующий read-only mount `./models:/models:ro`. Новый compose overlay `docker-compose.defense.yml` содержит только параметры defense-профиля.

## Benchmark и критерии выбора

Фиксированный локальный набор содержит минимум:

- 5 английских фраз;
- 5 русских фраз;
- 5 фраз с терминами FastAPI, WebSocket, React, TypeScript, NLLB, Whisper;
- 3 code-switch фразы.

Для STT фиксируются распознанный текст, WER/term accuracy, время обработки и real-time factor. Для MT фиксируются результат, term accuracy и latency. Для end-to-end фиксируются p50/p95 задержки и пиковое потребление памяти контейнеров.

Профиль принимается, если:

- EN → RU и RU → EN завершаются без ошибок;
- ключевые технические термины не исчезают;
- p95 end-to-end задержки не превышает 15 секунд;
- контейнеры не уходят в постоянный swap или restart;
- frontend остаётся отзывчивым;
- REST, WebSocket, audio pipeline и microphone/browser проверки проходят.

Если NLLB не укладывается в лимит, профиль автоматически или конфигурационно использует Marian для живой демонстрации, а fine-tuned NLLB показывается как отдельный quality benchmark. Это считается корректным fallback, а не неуспехом проекта.

## Этапы и коммиты

Каждый этап завершается отдельным Git-коммитом:

1. дизайн и план;
2. подготовка/конвертация моделей и воспроизводимый runbook;
3. тесты маршрутизации и mixed-language режима;
4. гибридная MT-маршрутизация;
5. defense compose-профиль и buffering;
6. glossary/произношение терминов;
7. benchmark и нагрузочные измерения;
8. финальный E2E verification report.

Большие файлы весов не добавляются в Git. В историю входят только конфигурация, код, тесты, скрипты и документация.
